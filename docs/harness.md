# 작업 하네스

이슈 하나 → PR 하나 → 3관점 리뷰 → 머지 → 다음 이슈. 이걸 반복한다.

## 명령

| 명령 | 하는 일 |
| --- | --- |
| `/poc-next [이슈번호]` | 다음 이슈 선택 → 구현 → PR 생성 |
| `/poc-review [PR번호]` | CI/CD · 실무도입 · 보안 3관점 병렬 리뷰 → PR 코멘트 |
| `/poc-merge [PR번호]` | 머지 → 이슈 클로즈 → 후속 이슈 차단 해제 |
| `/poc-loop [횟수]` | 위 셋을 멈춤 조건까지 자동 반복 |

## 리뷰 관점 3개

**CI/CD 전문가** (`.claude/agents/cicd-reviewer.md`)
재현성, 태그·버전 전파, 번들 크기, 멱등성, 롤백 경로, GitLab CI 문법.

**실무 도입** (`.claude/agents/adoption-reviewer.md`)
PoC에서 통한 게 고객사 100곳에서 왜 깨지는지. 사람 개입 지점, 암묵지,
버전 스큐, 인수인계 비용. 대부분의 지적은 "지금 고치자"가 아니라 "보고서에 남기자"다.

**보안/컴플라이언스** (`.claude/agents/security-reviewer.md`)
시크릿, 번들 변조 방지(체크섬 ≠ 서명), 최소 권한, 공급망, 감사 추적.
ERP는 회계·인사 데이터를 다루고 이 저장소는 public 이다.

세 관점이 충돌하면 그대로 드러내서 기록한다. 그 충돌이 보고서 6장의 재료다.

## 라벨 체계

| 라벨 | 뜻 |
| --- | --- |
| `type:repo` | PR로 완료. 루프가 자동 처리 |
| `type:env` | VM·레지스트리 수동 작업. **사람이 해야 함**, 결과를 이슈에 기록 |
| `type:measure` | 측정·기록 |
| `phase:0`~`phase:4` | plan.md 4장 실행 단계 |
| `H1`~`H8` | 기여하는 검증 가설 |
| `status:ready` / `status:blocked` | 선행 이슈 충족 여부 |
| `prio:must` / `should` / `conditional` | 축소 시 버리는 순서 |

라벨 재생성: `./scripts/bootstrap-labels.sh`

## 루프가 멈추는 지점

자동 루프는 아래에서 반드시 멈추고 사람을 부른다.

- `type:env` 만 남음 — 폐쇄망 VM 작업은 자동화 대상이 아니다
- 리뷰 3라운드에도 blocker 잔존 — 구현이 아니라 계획 문제일 수 있다
- **가설이 실패로 판정됨** — 실패는 유효한 결과다. 후속 이슈를 다시 짤지 결정 필요
- 이슈에 없던 작업이 필요 — 범위 확장은 사람이 결정한다

## 축소가 필요할 때

`plan.md` 4장의 원래 축소 순서(4단계 먼저 버림)는 잘못됐다.
4단계는 측정·원인기록·보고서이고, 그게 PoC의 산출물 자체다.

**버리는 순서: H7 → H8 → H2 커스텀 범위 축소. 4단계는 보존.**
