# 대역 외 배치물 (out-of-band)

이 디렉터리의 것들은 **번들에 들어가지 않는다.** 번들과 다른 경로·다른 시점으로
고객사 VM 에 1회 전달되어 미리 놓인다.

**로그의 문자 집합은 실행 환경에 종속되지 않는다.** 매니페스트 출력에서 제어문자만
지우고 비ASCII 는 보존한다 — `tr -cd '[:print:]'` 는 GNU `tr` 이 바이트 기반이라
로케일과 무관하게 한글을 삭제해서, 같은 번들의 한글 서명자가 Linux 에서만 사라진다.
**앵커는 3종이다.** 하나라도 빠지면 검출력이 떨어지고, 그 사실이 화면에 안 보인다.

| 배치물 | 무엇 | 빠지면 |
| --- | --- | --- |
| 공개키 (키링에 임포트) | 서명 검증의 기준 | exit 12 — 검증 자체 불가 |
| `verify-bundle.sh` | 검증 코드 | 번들 안 `install.sh` 만 돌게 되고 검증이 우회된다 |
| `expected-fingerprint` | 서명자 판정 기준 | **exit 0 으로 통과하되 키링의 아무 키로나 통과한다** |
| 종료 코드 표 (아래) | 고객사 담당자용 1장 | 전화 통화가 3분에서 30분이 된다 |

`test-verify-bundle.sh` 는 고객사에 가지 않는다. 개발 측 산출물이다.

## 왜 번들 밖이어야 하는가

공개키와 검증 코드가 번들과 같은 매체로 이동하면, 운반 구간에 접근한 사람이

1. 이미지에 백도어를 넣고
2. **자기 키로 재서명한 뒤**
3. 번들 안의 공개키와 `install.sh` 를 자기 것으로 바꿔치기

하면 그만이다. 고객사 설치 스크립트는 "검증 OK" 를 출력하고 정상 설치한다.
**검출력이 체크섬만 있을 때와 같아진다.**

공개키만 밖으로 빼는 것도 절반이다 — 번들 안 `install.sh` 의 `gpg --verify` 호출을
지우면 사전 배치한 키는 아무도 읽지 않는다. **검증하는 코드도 밖에 있어야 한다.**

## 신뢰 경계

```
   [ 우리 ]                     [ 운반 구간 ]              [ 고객사 VM ]
                                                        ┌──────────────────┐
   공개키 + verify-bundle.sh ───── 대역 외 1회 ────────▶ │ 신뢰 경계 안쪽    │
                                  (계약 시점 대면 전달,   │  · 공개키         │
                                   지문 별도 채널 확인)   │  · verify-bundle │
                                                        │  · 기대 지문      │
   번들.tar + .sha256 + .asc ──── USB · 파일전송 ──────▶ │──────────────────│
                                  (변조 가능 구간)       │ 검증 대상         │
                                                        └──────────────────┘
```

**번들 안 `install.sh` 도 서명 대상이다.** 서명이 tar 전체를 덮으므로 그렇게 되고,
`verify-bundle.sh` 가 그 사실을 확인해 로그에 남긴다.

**`.asc` 자체는 서명되지 않은 컨테이너다.** 운반 구간에서 서명 블록을 덧붙일 수 있으므로
유효 서명 **개수와 서명자 전부**를 로그에 남기고, 그중 하나라도 앵커와 맞으면 통과한다.
첫 서명만 보면 공격자가 번들을 건드리지 않고 자기 서명을 앞에 덧붙이는 것만으로
exit 14("즉시 연락")를 반복 생성할 수 있다 — 거짓 경보가 반복되면 그 경로가 안 믿긴다.

## 번들 레이아웃 계약

두 구조를 **둘 다** 받는다. 어느 쪽을 쓸지는 #19 의 미결 ADR 이고, 검증 스크립트가
그 결정을 대신 내리지 않는다.

```
(A) 묶음 매니페스트                    (B) 버전별 매니페스트
    manifest.json      <- 묶음 신원        v1.0/manifest.json
    v1.0/install.sh                        v1.0/install.sh
    v1.2/install.sh                        v1.2/manifest.json
    v1.3/install.sh                        v1.2/install.sh
    images.tar                             ...
```

규칙은 둘뿐이다.

- `install.sh` 가 **최소 1개** 있어야 한다 (없으면 exit 15)
- **버전 디렉터리**(하위 디렉터리)에 매니페스트가 있으면 그 디렉터리에 `install.sh` 도
  있어야 한다 (없으면 exit 15). 최상위 매니페스트는 묶음 신원이지 버전이 아니므로
  이 규칙에서 제외된다

매니페스트가 하나도 없어도 통과하되 **경고**한다 — 번들 신원이 감사 로그에 남지 않는다.

## 실행 계정

`/var/log/erp-verify.log` 와 `/etc/erp-deploy/` 를 다루므로 `sudo` 로 도는 것이 자연스럽다.
다만 **root 로 돌리면 "지문 파일을 읽을 수 없음"(exit 5) 분기는 발화하지 않는다** —
root 는 `chmod 000` 파일도 읽는다. 어떤 계정으로 실행할지 정하고, 2단계 7번 ⑦ 의 앵커
확인 절차에 실행 계정과 지문 파일 소유자·모드를 함께 기록하라.

## 사용

```sh
verify-bundle.sh <번들.tar>      # 같은 디렉터리에 .sha256 과 .asc 가 있어야 한다
```

**통과한 뒤에만** 번들을 풀고 안의 `install.sh` 를 실행한다. 순서를 지키지 않으면
검증되지 않은 스크립트를 실행하는 것이고, 그건 검증이 없는 것과 같다.

## 종료 코드

원인을 구분한다. 폐쇄망 고객사 담당자는 "설치가 안 돼요" 라고만 말할 수 있으므로,
무엇이 왜 실패했는지가 화면과 로그(`/var/log/erp-verify.log`) 양쪽에 남아야 한다.

| 코드 | 원인 | 고객사가 할 일 |
| --- | --- | --- |
| 0 | 통과 | 설치 진행 |
| 1 | 내부 오류 (분류되지 않은 종료) | **재운반 불필요.** 로그 전문과 함께 공급사에 문의 |
| 2 | 번들·체크섬·서명 파일 없음 | 운반 매체 확인 |
| 3 | 로그를 기록할 수 없음 | 화면의 `sudo` 명령 실행, 또는 `ERP_LOG` 지정 |
| 4 | gpg 또는 tar 미설치 | **재운반 불필요.** VM 사전 요구사항 문제 — 공급사 문의 |
| 5 | 앵커 설정 오류 (지문 파일 비었음·읽기 불가·지정 경로 없음) | 지문 재요청. **번들에 딸려온 안내서를 따르지 말 것** |
| 6 | 체크섬 파일 형식 불명 | **재운반 불필요.** 생성 측 문제 — 공급사 문의 |
| 10 | 체크섬 불일치 | 재운반 |
| 11 | 서명 불일치 | **설치 금지.** 즉시 연락 |
| 12 | 공개키 없음 | 앵커 미배치. **번들 안의 키를 임포트하지 말 것** |
| 13 | 서명 키 만료 | 공급사에 키 회전 확인 (일정 문제) |
| 14 | 기대 지문과 서명자 불일치 | **설치 금지.** 즉시 연락 |
| 15 | 번들 구조 이상 | **재운반 불필요.** 공급사 문의 |
| 16 | 서명 키 폐기 | **설치 금지.** 즉시 연락 (사고) |
| 130 | 중단됨 (Ctrl-C · 세션 끊김 · 타임아웃) | **재운반 불필요. 재실행하십시오** |

**종료 코드는 닫힌 집합이다.** 표에 없는 코드가 나오지 않도록 `trap` 으로 미분류 종료를
`1` 로 정규화하고, 신호(`INT`/`TERM`/`HUP`)는 `130` 으로 모은다. 자동화의 인터페이스가
종료 코드인 이상, 표가 전수가 아니면 계약이 아니다.

**`130` 을 `1` 로 접지 않는 이유**: 수백 MB 해싱에 시간이 걸려 세션 끊김·타임아웃이
현실적인 종료 사유다. `1`("공급사 문의")로 접으면 **자기가 끊은 검증 때문에 공급사에
전화하게 된다.** 130 은 재실행이 정답이다.

**재운반이 고치는 것은 10 뿐이다.** 나머지에 재운반을 시키면 왕복만 늘어난다.
만료(13)와 폐기(16)를 나눈 이유도 같다 — 만료는 일정이고 폐기는 사고이며,
자동화가 읽는 것은 종료 코드지 한국어 문장이 아니다.

## 기대 지문

`gpg --verify` 는 **키링의 아무 키로나 성공한다.** 고객사 운영자가 지원 과정에서
다른 키를 임포트하는 순간 그 성공은 의미가 없어진다. 그래서 지문 대조가 판정이다.

- `ERP_EXPECTED_FPR` 환경변수, 또는
- `/etc/erp-deploy/expected-fingerprint` 파일 (`ERP_FPR_FILE` 로 변경 가능)

**파일이 있으면 그것이 최종 판정값이고 환경변수는 무시된다.** 앵커 값은 앵커 쪽에서만
온다. 환경변수로 덮을 수 있으면, 운반 구간에 안내서를 한 장 끼워 넣는 것만으로
("실행 전 `export ERP_EXPECTED_FPR=…`") 공격자 서명 번들이 **"지문 일치" 를 화면과
감사 로그에 남기며** 통과한다. 검증 없음보다 나쁘다 — 거짓 보증을 문서화한다.
**`ERP_FPR_FILE` 도 마찬가지다.** 사전 배치 앵커가 있으면 무시하고, 없으면 exit 5 로 거부한다.
공격자는 *없는* 경로를 지정하지 않는다 — 자기 지문 파일을 번들에 동봉하고 그걸 가리키게 한다.
개발·테스트용 재지정은 `ERP_ALLOW_UNSAFE_ANCHOR=1` 을 함께 줘야 하고, 그 경우 판정 줄에
`(앵커 우회 모드)` 가 찍힌다.

**PoC 에서도 반드시 배치한다.** 배치하지 않으면 `plan.md` 7번 ⑧(b)(다른 키로 전체
재서명)가 exit 0 을 내고, **H3 의 변조 검출 절반이 `거짓` 으로 기록된다.**

등록값은 **primary 키 지문**을 쓴다. 아래 명령이 그 값을 공백 없이 뽑는다:

```sh
gpg --list-keys --with-colons | awk -F: '/^pub/{p=1}/^fpr/{if(p){print $10;p=0}}'
```

`gpg --fingerprint` 출력(`2342 0B57 …`)을 그대로 붙여넣어도, CRLF 로 저장돼도,
소문자로 적어도 통과한다 — 정규화한다. 전용 서명 서브키로 서명된 경우도 primary 로
대조되며 서브키 지문을 등록해도 통과한다.

## 이 스크립트를 갱신할 때

`verify-bundle.sh` 는 `SCRIPT_VERSION` 을 갖고 로그 첫 줄에 찍는다. 고객사가 로그
한 줄을 읽어주면 어느 버전이 돌았는지 특정된다.

**앵커 갱신은 키 회전과 같은 비용 구조다** — 원격 불가, 물리 방문 또는 담당자 손.
스크립트에 결함이 나오면 고객사 N곳에 새 파일을 다시 대역 외로 넣어야 한다.
`docs/findings.md` 의 앵커 비용 산식이 `(키 회전 + 스크립트 개정) × 고객사 수` 인 이유다.

## 테스트

```sh
./test-verify-bundle.sh
```

임시 디렉터리와 임시 키링에서만 동작한다. 시스템 키링을 건드리지 않는다.
성공 경로 하나로는 아무것도 증명하지 못하므로 — `gpg --verify || true` 가 한 줄
들어가 있어도 성공 경로는 통과한다 — 실패 경로를 전부 돌린다.
