PoC 하네스의 **자동 루프**. 아래를 멈춤 조건에 걸릴 때까지 반복한다.

$ARGUMENTS 에 숫자가 있으면 그 횟수만큼만 돈다. 없으면 멈춤 조건까지 계속.

## 한 사이클

1. **`/poc-next`** — 다음 이슈 선택 → 구현 → PR
2. **`/poc-review`** — 3개 관점 병렬 리뷰
3. blocker 가 있으면:
   - 지적을 수정하고 같은 브랜치에 push
   - `/poc-review` 재실행 (라운드 번호를 올려서 전달)
   - **최대 3라운드.** 3라운드에도 blocker 가 남으면 멈추고 사람을 부른다.
     같은 지적이 세 번 반복되는 건 구현 문제가 아니라 계획 문제일 가능성이 높다.
4. **`/poc-merge`** — 머지 → 이슈 클로즈 → 후속 차단 해제
5. 사이클 결과를 한 줄로 보고하고 1로 돌아간다

## 멈춤 조건

아래 중 하나라도 해당하면 **즉시 멈추고 사람에게 보고**한다. 우회하지 마라.

- `status:ready` 인 `type:repo` 이슈가 없다 (남은 게 `type:env` 뿐이거나 전부 끝)
- 리뷰 3라운드에도 blocker 가 남았다
- CI 정적 검증이 두 번 연속 실패하고 원인을 못 찾았다
- `plan.md` 와 이슈 완료 조건이 충돌해서 어느 쪽을 따를지 판단이 필요하다
- 가설이 **실패로 판정**됐다 (예: H5 롤백 불가 확인)
  → 이건 성공이다. `plan.md` 는 실패도 유효한 결과로 설계했다.
    결과를 `docs/findings.md` 에 기록하고, 후속 이슈들이 그 실패를 전제로
    다시 짜여야 하는지 사람에게 물어라. 조용히 다음으로 넘어가지 마라.
- 이슈에 없던 작업이 필요하다는 판단이 든다
  → 임의로 하지 말고 새 이슈를 제안하고 멈춰라. 범위 확장은 사람이 결정한다.
- 같은 파일을 세 사이클 연속으로 고치고 있다 (설계가 잘못됐다는 신호)

## 매 사이클 지켜야 할 것

- **결과를 부풀리지 마라.** 실행 못 한 검증은 "미실행"이라고 쓴다. PoC의 가치는
  뭐가 됐는지가 아니라 뭐가 안 됐는지를 정확히 아는 데 있다.
- 측정값이 나오면 그 자리에서 `measurements/` 에 기록한다. 나중에 몰아서 하면
  4단계에서 전부 다시 재현해야 한다.
- `docs/findings.md` 에 리뷰의 `report` 항목을 누적한다.
- 커밋 메시지와 PR 본문은 한국어로 쓴다.

## 최종 보고

멈출 때 아래를 정리해 보고한다.

- 이번 실행에서 머지한 PR과 닫힌 이슈
- 가설별 현재 상태 (H1~H8: 검증됨 / 실패 / 미착수)
- 사람이 처리해야 할 `type:env` 이슈 목록
- 멈춘 이유와 다음에 필요한 결정
